# 产品需求与范围

## 1. 产品定位

TestBuddy 是一个面向单个使用者、运行在本地桌面端的 Web UI 智能自动化测试工具。

它的核心价值不是临时完成一次浏览器操作，也不是生成一段难以维护的脚本，而是：

> 让用户先用自然语言探索和验证业务路径，再把确认过的结果沉淀为可长期运行、可审阅、可版本化的回归资产。

自然语言是主入口。录制和 PRD/PDF 不是与自然语言并列的产品中心，而是向同一条资产生成链路提供上下文的输入适配器：

```text
自然语言目标
  + 可选录制路径
  + 可选 PRD / 验收标准
  -> 探索运行
  -> 用户确认
  -> Hybrid Case
  -> Suite 回归
  -> 维护队列
```

当前产品已经具备本地工作台、自然语言 Agent Run、录制/PRD 输入、运行记录和桌面/CLI 执行基础。本文描述目标产品契约；哪些能力已实现、仅完成离线验证或仍需真实页面验收，以 [自动化测试 Agent 进度与目标状态](./agent-progress-and-target.md) 为准。

## 2. 目标用户与核心任务

### 2.1 目标用户

核心用户是独立维护一个或多个 Web 项目的测试工程师、开发工程师或产品质量负责人。

共同特征：

- 在自己的电脑上创建和运行测试。
- 希望用自然语言快速验证页面，而不是先学习脚本 API。
- 需要把一次有效探索变成可以反复执行的回归用例。
- 可以自行管理项目目录，并可选择用外部 Git 管理其中的测试资产。

产品不以团队协作、组织管理或云端测试平台为前提。

### 2.2 核心任务

1. 在 15 分钟内从一个 Web 地址和一句自然语言目标得到首个可复跑用例。
2. 审阅 Agent 探索出的动作、目标和断言，将其确认为 Hybrid Case。
3. 使用桌面端或 CLI 运行 10–100 条用例组成的 Suite，并得到一致结果。
4. 在页面变化后收到可审阅的维护草稿，而不是让 AI 静默改写既有资产。
5. 通过证据、运行状态和 flaky 标记判断失败属于业务问题、环境阻塞还是资产维护问题。

## 3. 产品原则

### 3.1 确定性优先

- 已确认的回归用例默认执行结构化动作和显式断言。
- 可以用公开、稳定的页面契约完成的动作，不在每次运行时重新交给模型解释。
- AI 只用于探索、受控恢复和确定性规则无法覆盖的复杂判断。
- AI 恢复不能自动修改用例、基线、fixture 或公共流程。
- 登录、提交、删除、支付、审批等高风险动作即使恢复，也不能改变原用例的业务语义、目标对象或断言口径。

### 3.2 用户确认后才成为资产

- 自然语言探索结果先形成草稿。
- 用户需要确认结构化动作、目标和断言，才能保存为正式用例。
- 录制和 PRD 生成的内容同样先进入草稿，不直接成为可信回归资产。
- 维护建议必须进入维护队列，由用户审阅、接受或丢弃。

### 3.3 本地、可携带、可外部版本管理

- 长期资产保存在用户选择的 project directory。
- 运行记录、临时产物、凭证和缓存保存在应用管理的 `studio-data`。
- TestBuddy 不内置 Git；用户可自行用任意外部 Git 工作流管理 project directory。
- 桌面端和 CLI 使用同一 Runner 和同一资产语义。

## 4. 产品信息架构

### 4.1 应用级结构

- 启动屏与设置
- 首页与维护队列摘要
- 项目目录
- 自然语言测试
- 用例与 Suite
- Fixtures / 认证
- 公共流程
- 录制输入
- PRD 输入
- 运行记录与产物

自然语言测试是主执行入口。录制和 PRD 页面负责采集、解析和预览输入，最终都生成同一种待确认用例草稿。

### 4.2 启动屏与设置

首次加载显示独立启动屏，负责：

- 选择或创建 project directory。
- 检查本地浏览器和 Runner 环境。
- 可选配置 Midscene / 模型供应商。
- 允许跳过模型配置；纯确定性用例不应因此被拦截。
- 当用户进入确实需要 AI 的探索、恢复或复杂判断时，再明确提示配置缺口。

### 4.3 首页

首页是本地项目的工作摘要，不负责复杂编辑。

重点展示：

- 最近 Suite 和用例结果。
- `blocked`、`error` 和 flaky 风险。
- 待审阅的用例草稿、恢复草稿和公共流程影响项。
- 即将按保留策略清理的产物。
- 自然语言测试主入口。

### 4.4 自然语言测试

用户选择项目和环境后输入业务目标，例如：

> 登录后台，筛选近 30 天订单，确认列表只包含已支付订单，并把这条路径保存为每日回归。

系统需要：

1. 明确目标、前置条件和潜在高风险动作。
2. 在受控浏览器中探索执行。
3. 展示实际动作、定位目标、断言、证据和 AI 介入点。
4. 让用户删除、修改或确认步骤与断言。
5. 保存为版本化 Hybrid Case，或仅保留本次运行记录。

### 4.5 录制与 PRD 输入适配器

录制适配器负责把真实操作转为候选动作和上下文定位指纹；PRD 适配器负责把需求原文和验收标准转为候选意图与断言。

两者共同遵守：

- 输出必须可追溯到录制节点或 PRD 原文。
- 输出只是草稿，不绕过用户确认。
- 不创建独立于 Hybrid Case 的第二套回归语义。
- 生成资产后仍保留来源引用，便于后续影响分析。

## 5. Hybrid Case

### 5.1 定义

Hybrid Case 是 TestBuddy 的核心长期资产，由三部分组成：

1. **业务意图**：用人可读语言说明为什么测、成功意味着什么。
2. **用户确认的结构化动作与目标**：动作类型、目标页面、定位指纹、输入来源、前置条件和风险级别。
3. **显式版本化断言**：每条断言有稳定 ID、版本、期望值、证据要求和变更原因。

示意：

```text
Case: 已支付订单筛选
Intent: 运营人员筛选“已支付”后，只看到已支付订单
Actions:
  - navigate: /orders
  - select: 状态筛选器 -> 已支付
Assertions v3:
  - network: GET /api/orders?status=paid 成功
  - table: 状态列所有完整证据均为“已支付”
```

### 5.2 执行策略

- 确定性动作和断言优先执行。
- 定位失效时可按既有定位指纹做受控候选匹配。
- 候选仍不可靠时才请求 AI 恢复。
- 复杂视觉、图表语义或跨区域业务判断可以显式标记为 AI 判断。
- AI 判断必须保存输入证据、结论和置信边界；证据不足时不能记为通过。
- AI 恢复成功只影响本次运行。系统可以生成维护草稿，但不能自动提升为新版本。

### 5.3 高风险动作

高风险动作包括但不限于提交、删除、支付、审批、发送通知和修改生产数据。

恢复时必须满足：

- 不替换业务对象。
- 不扩大操作范围。
- 不改变提交内容。
- 不跳过原断言或把失败条件改成更宽松的条件。
- 无法证明等价时停止，并把运行标记为 `blocked` 或 `failed`，而不是继续猜测。

## 6. 定位契约

TestBuddy 不要求被测应用添加 `data-testid`。

定位优先依据：

1. 语义 HTML 与可访问名称，例如 `button`、`label`、`name`。
2. ARIA role、name、state 和 relationship。
3. 公开 DOM 中稳定的 `id`、`href`、表头、表单属性和业务标识。
4. 上下文定位指纹，包括页面路径、landmark、父级标题、相邻文本、目标语义和候选公开属性。

每个结构化目标都需要保存定位质量：

- 使用了哪些公开信号。
- 是否存在唯一匹配。
- 是否依赖易变文本、位置或框架私有 class。
- 是否有可解释的备用候选。

`data-testid` 已存在时可以作为普通公开 DOM 信号使用，但不能成为接入 TestBuddy 的前置要求，也不能掩盖低质量语义结构。

## 7. 项目资产与运行数据

### 7.1 Project directory

用户选择的 project directory 保存需要长期维护、审阅和可选外部版本管理的资产：

```text
<project-directory>/
  project.json
  cases/
  suites/
  fixtures/
  reusable-flows/
  baselines/
```

- `cases/`：Hybrid Case 与断言版本。
- `suites/`：用例集合、顺序、并发和资源锁声明。
- `fixtures/`：typed fixture 定义及其 setup / cleanup 声明。
- `reusable-flows/`：固定版本的公共流程。
- `baselines/`：用户确认的视觉或结构基线。

Project directory 不保存 API Key、认证状态、运行截图、trace 或缓存。TestBuddy 只提供文件读写和一致性校验，不实现 Git 操作。

### 7.2 `studio-data`

`studio-data` 是应用管理的运行时数据根目录：

```text
studio-data/
  runs/
  artifacts/
  credentials/
  cache/
```

- `runs/`：运行摘要、步骤结果、状态和维护候选。
- `artifacts/`：截图、trace、下载文件、diff 和报告。
- `credentials/`：加密凭证引用和认证 `storageState`。
- `cache/`：可重建索引、解析结果和浏览器缓存。

运行数据不能反向成为 project asset 的唯一来源；资产修改必须经过显式保存。

## 8. Fixtures 与认证

### 8.1 Typed fixtures

Fixture 必须声明：

- 稳定 ID 和版本。
- 输入参数及类型。
- 输出值及类型。
- 所需凭证引用。
- setup 和 cleanup。
- 可并发性与资源锁。
- 执行方式和信任要求。

默认优先使用 HTTP 完成测试数据准备和清理，因为它更快、更稳定，也更容易确认副作用。浏览器 UI setup 只在没有稳定 HTTP 能力时使用。

### 8.2 脚本信任

Project directory 中的自定义脚本默认不执行。

首次执行或脚本内容/哈希变化后，用户必须显式信任。信任提示需要展示脚本路径、用途、所需环境变量和可能副作用。未信任脚本使相关用例进入 `blocked`，不能自动降级或绕过。

### 8.3 认证

- 浏览器认证以 Playwright `storageState` 为主要复用形式。
- Project asset 只保存凭证和 `storageState` 的引用，不保存秘密内容。
- 认证过期应标记为 `blocked` 并提供刷新入口。
- setup 失败后仍应按能力尝试 cleanup，并分别记录两者结果。

## 9. Suite 与 Runner

### 9.1 Suite 规模

目标工作负载是单机运行 10–100 条用例的 Suite。

Suite 支持：

- 按标签、目录或显式列表选取用例。
- 声明顺序依赖。
- 配置本地有限并发。
- 对共享账号、租户、环境、fixture 或其他互斥资源加锁。
- 设置失败继续、失败停止和重试策略。

### 9.2 Runner 一致性

- 桌面端与 CLI 调用同一个 Runner，不分别实现调度和状态推导。
- Runner 在命令或桌面运行期间存在，结束后退出。
- 不引入常驻后台 daemon。
- CLI 与桌面端读取相同 project directory，并把运行数据写入相同 `studio-data` 契约。

### 9.3 结果状态

终态必须区分：

- `passed`：所有必需动作和断言完成且通过。
- `failed`：被测业务行为或显式断言不满足预期。
- `blocked`：凭证、环境、未信任脚本、前置条件或资源使测试无法开始/继续。
- `skipped`：由 Suite 选择、条件或依赖策略明确跳过。
- `cancelled`：用户或上层调用主动取消。
- `error`：Runner、浏览器、文件或基础设施异常，不能归因于业务断言。

`flaky` 是独立标记，不是第七种状态。一次运行仍保留真实终态；当相同资产在等价条件下出现不一致结果或需要重试才通过时，附加 flaky 标记和证据。

## 10. 浏览器与交互范围

### 10.1 浏览器支持

- Chromium 是稳定支持基线。
- Firefox 和 WebKit 标记为实验性；结果必须显示实验性标识，不能与 Chromium 稳定性承诺等同。

### 10.2 交互能力

目标 Web UI 范围包括：

- iframe 内定位与交互。
- 多 tab / popup 的受控切换。
- 文件上传。
- 下载等待、校验和产物归档。
- hover。
- drag and drop。
- clipboard 读写。
- 网络请求/响应断言。
- 用户显式声明的网络 mock。

网络 mock 不得隐式启用。mock 规则必须作为可审阅资产声明作用域、匹配条件、返回内容和启停状态，并在运行记录中明确标记。

## 11. 公共流程与影响分析

公共流程用于复用登录、导航、创建基础数据等稳定步骤。

- 每个 reusable flow 有稳定 ID 和不可变版本。
- 用例固定引用具体版本，不自动跟随 latest。
- 修改公共流程时创建新版本。
- 升级前展示受影响的用例、Suite、fixture 和基线。
- 批量升级必须由用户确认，并形成可审阅 diff。
- 旧版本在仍被引用时不能被静默删除。

## 12. 维护、安全与保留

### 12.1 维护队列

以下情况进入维护队列：

- 定位质量下降或只能依赖 AI 恢复。
- 断言证据结构发生变化。
- 基线差异超过阈值。
- fixture、认证或公共流程版本过期。
- 同一用例被标记 flaky。

队列项包含原失败证据、建议目标、候选动作/断言变更和影响范围。接受队列项会创建资产新版本；拒绝不会改变原资产。

### 12.2 脱敏

- API Key、密码、token、cookie、Authorization 头和用户配置的敏感字段在写入日志、截图元数据、报告或模型请求前脱敏。
- 截图和下载文件可能包含业务敏感信息，必须有明确标识和受控打开/导出。
- 模型只接收完成当前任务所需的最小证据。

### 12.3 保留策略

- runs、trace、截图、下载和报告可分别配置保留策略。
- 清理前显示影响范围；被固定、被维护项引用或作为当前基线的产物不得自动删除。
- 凭证和 `storageState` 使用独立生命周期，不随普通 artifact 清理。
- 清理运行产物不能删除 project directory 中的长期资产。

## 13. 非功能要求

### 13.1 可解释性

- 每一步都记录来源、实际目标、定位质量、执行方式和证据。
- 明确标记 AI 参与的规划、恢复或判断。
- 失败必须定位到具体动作、断言或基础设施阶段。

### 13.2 稳定性

- 在页面结构稳定、数据和环境等价的前提下，确定性用例应可重复得到相同结果。
- 重试不能掩盖业务失败；重试后通过需要独立 flaky 标记。
- Suite 并发必须受本机资源和显式资源锁约束。

### 13.3 可维护性

- 用例、断言、fixture、公共流程和基线均有稳定 ID 与版本关系。
- AI 不直接改资产。
- 任何批量升级都先做影响分析。

## 14. 明确非目标

当前产品不实现：

- 多人协作、账号体系和 RBAC。
- 云同步或托管测试资产。
- 分布式执行、云真机矩阵或常驻调度服务。
- 内置 Git 客户端、提交、分支或合并能力。
- 完整 API 测试平台。
- 移动端自动化。
- 性能/压测平台。
- 验证码绕过或破解。
- 跨桌面应用自动化。

## 15. 阶段依赖

正式推进顺序为：

1. Regression Case V2。
2. Project Asset Store。
3. Fixtures / Auth。
4. Suite Runner。
5. Reusable Flows。
6. Maintenance / Safety。
7. Interaction Breadth。
8. Real Acceptance。

后续阶段依赖前序资产契约稳定：Suite Runner 不应先于 project asset store；公共流程不应先于用例和 fixture 版本语义；真实验收不替代前序离线门禁。详细交付和门禁见 [实施路线图](./implementation-roadmap.md)。

## 16. 产品完成定义

目标版本必须同时满足：

- **首用例时间**：新用户从选择项目目录到保存并成功复跑首个 Hybrid Case 不超过 15 分钟。
- **Suite 一致性**：同一份 20 case Suite 在桌面端和 CLI 使用同一配置运行，选取用例、调度语义、终态和报告口径一致。
- **稳定性**：对结构稳定的页面，在等价数据和环境下连续运行 10 轮，干净通过率不低于 95%；需要重试才通过的轮次不计为干净通过。
- **可维护性**：页面变化导致定位或断言失效时，系统保留原资产和失败证据，并形成可审阅的维护草稿，不自动改写业务语义。
